Prototype versioning & design history

How to create new prototype versions and document design changes

Overview

This prototype uses two main workflows:

  1. Create a new prototype version – Scaffold folder structure, routes, and metadata for design iteration
  2. Document design history – Record design changes, decisions, and research findings

Both are supported by Copilot skills that automate repetitive setup tasks, letting you focus on design and content.

Skill 1: Create a new prototype version

What it does

Scaffolds a complete new version with folder structure, route files, and metadata entry.

Invoke: @copilot #create-prototype-version

Use when

  • Starting a new design iteration (e.g., v3.9.0.0)
  • Testing a concept with a copy of existing version
  • Ready to prototype but tags/pages not yet finalized

Workflow: from idea to published card

Step 1: Scaffold (Copilot runs this)

Run the skill and provide:

  • Version number (e.g., 3.9.0.0)
  • Type: release / in-development / research
  • Date: "TBC" initially, update later
  • Tags: empty OK, add as you design
  • Pages: empty OK, add as you create views

Copilot creates:

  • Folder: /app/views/v3-9-0-0/
  • Route file: /app/routes_v3-9-0-0.js
  • Updated: /app/routes.js (adds route)
  • HTML card template (ready to copy)
  • Entry in: app/views/versions.json
Step 2: Design (you do this)

Build your prototype views iteratively:

  1. Create views in /app/views/v3-9-0-0/
  2. Add routes to /app/routes_v3-9-0-0.js as you create pages
  3. Test locally

Don't worry about: metadata is flexible and can be updated anytime

Step 3: Update metadata (as you go)

Edit app/views/versions.json with your design progress:

Add a feature tag:

"tags": ["boundary-upload", "map-styling"]

Add pages as you create them:

"pages": [
  { "name": "Start page", "url": "/v3-9-0-0/" },
  { "name": "Map page", "url": "/v3-9-0-0/map" }
]

Update date when confirmed:

"date": "Release - 22 January 2026"

The card updates automatically — no manual HTML editing needed.

Step 4: Publish card (when ready)

Copilot generated HTML card template earlier. When version is ready to show:

  1. Copy the generated card HTML
  2. Paste into app/views/index.html in the versions grid
  3. Commit to git

Card structure is consistent with existing versions — tags, pages, and links all update from JSON automatically.

Step 5: Link design history (when post exists)

After design history post is published, update versions.json:

"designHistoryUrl": "/design-history/3-9-0-0/"

Card now links to full design documentation.

Skill 2: Create a design history entry

What it does

Scaffolds folder structure, post template, and metadata for documenting design changes, releases, or research findings.

Invoke: @copilot #design-history-entry

Use when

  • Release is ready to document (what changed, why, screenshots)
  • Research findings need recording (what users struggled with, solutions tested)
  • Design iteration reaches a milestone worth explaining

Workflow: from research to published post

Step 1: Prepare content (you do this)

Before running the skill, gather:

  • Screenshots/images (PNG format, max 2MB each, descriptive alt text)
  • Design narrative (what changed and why, 100-500 words)
  • Version identifier (e.g., 3.9.0.0 or draw-boundary-research)
  • Type: release / research
  • Date (e.g., "22 January 2026")
  • Feature tags (e.g., boundary-upload, map-styling)
Step 2: Run skill (Copilot does this)

Run the skill and provide:

  • Version identifier
  • Type (release or research)
  • Date
  • Title/heading
  • Summary (one-liner)
  • Feature tags

Copilot creates:

  • Folder: /app/views/design-history/3-9-0-0/
  • Post template: index.html with structure ready for content
  • Entry in: app/views/design-history/posts.json
  • Breadcrumb navigation set up
Step 3: Write content (you do this)

Edit the post template with your design narrative:

  1. Add introductory paragraph (context and goals)
  2. Add section for each key change/finding
  3. Add screenshots with descriptive captions
  4. Use heading hierarchy (h2 for major sections, h3 for subsections)
  5. Keep alt text meaningful: "Screenshot of new boundary drawing menu showing options for freehand vs polygon"

Structure: narrative + images, not a list. Tell the story of the design.

Step 4: Publish (when ready)

Once content is complete:

  1. Verify all images are added and alt text is descriptive
  2. Check breadcrumb navigation (should link: Home → Design history → This post)
  3. Test links to prototype versions
  4. Commit to git

Post is now live at /design-history/3-9-0-0/ and linked from version card.

Complete workflow: idea to launch

  1. Have a design idea (new version, iteration, or research round)
    • Decide version number and type
  2. Run create-prototype-version skill
    • Scaffold folder and routes
    • Create metadata entry with empty tags/pages
  3. Design iteratively
    • Create views in version folder
    • Add routes to route file
    • Update tags/pages in versions.json as you go
  4. Publish version card (when you want it visible on home page)
    • Copy generated HTML card into index.html
    • Commit
  5. Document the design (when there are changes worth explaining)
    • Run design-history-entry skill
    • Write narrative with screenshots
    • Publish post
  6. Link design history (after post is live)
    • Update designHistoryUrl in versions.json
    • Version card now links to full documentation

Design history-only versions

Sometimes you want to document a release or research finding without building a working prototype. For example:

  • A release that only involved backend changes (no new user interface)
  • A research round where the findings are documented but prototype was never built
  • A version that has been sunsetted and is kept for historical reference only

For these cases, create a version card without a prototype link.

Setting up a design history-only version

In versions.json:

{
  "number": "3.6.1",
  "type": "release",
  "date": "Release - 22 January 2026",
  "tags": ["draw-boundary", "map-query"],
  "pages": [],
  "prototypeUrl": null,
  "hasPrototype": false,
  "designHistoryUrl": "/design-history/3-6-1/"
}

Key fields:

  • "pages": [] – Leave empty (no prototype pages to list)
  • "prototypeUrl": null – No prototype to link to
  • "hasPrototype": false – Indicates this is documentation only
  • "designHistoryUrl": "/design-history/3-6-1/" – Link to the design history post

Card display

The version card will display:

  • Version number, date, and tags (filtered as normal)
  • "No prototype" text instead of a "View prototype" link
  • Design history link so users can access full documentation
  • No "Pages in this version" section (empty pages array)

All version data lives in app/views/versions.json. This is the single source of truth.

Example entry 
{
  "number": "3.9.0.0",
  "type": "release",
  "date": "Release - 22 January 2026",
  "tags": ["boundary-upload", "map-styling"],
  "pages": [
    { "name": "Start page", "url": "/v3-9-0-0/" },
    { "name": "Map page", "url": "/v3-9-0-0/map" }
  ],
  "prototypeUrl": "/v3-9-0-0/",
  "designHistoryUrl": "/design-history/3-9-0-0/"
}
versions.json fields
Field Type Example Notes
number String 3.9.0.0 Semantic versioning
type String release, in-development, research Determines card formatting and date prefix
date String Release - 22 January 2026 Use "TBC" initially, update when confirmed
tags Array ["boundary-upload", "map-styling"] Feature tags, used for filtering. Start empty.
pages Array of objects [{"name": "Start page", "url": "/v3-9-0-0/"}] List of pages in this version. Start empty.
prototypeUrl String or null /v3-9-0-0/ Link to start page of version. Set to null for design-history-only versions.
hasPrototype Boolean true or false Set to false for versions documented only in design history (no working prototype)
designHistoryUrl String or null /design-history/3-9-0-0/ Add after design history post is published

For other designers & teams

This approach is designed to be reusable. Here's what you can adapt:

Core concept

Separate concerns: Prototype versions (for design exploration) and design history (for documentation) are distinct workflows supported by automation, not manual card editing.

Key files to reference

  • Skill: Create Prototype Version – .github/skills/create-prototype-version/SKILL.md
  • Skill: Design History Entry – .github/skills/design-history-entry/SKILL.md
  • Metadata Source – app/views/versions.json
  • Home Page – app/views/index.html (card HTML structure)
  • Design History Index – app/views/design-history/index.html

Adaptable elements

  • Metadata schema – Add/remove fields in versions.json and posts.json as needed
  • Card template – Modify HTML structure for different designs (but keep consistent)
  • Route scaffolding – Adjust for your router setup (this uses Express.js)
  • Date formatting – Customize "Release - " prefix or date display
  • Tag filtering – JavaScript filter logic in index.html can be styled differently

    • Common adaptations

    • Different metadata – Add fields like "owner", "research-phase", "team"
    • Multiple prototype types – Split into "variants", "experiments", "releases"
    • Integrated design system – Embed design tokens/component library metadata
    • Research tracker – Extend to track research sessions, participants, insights

    Best practices

    Metadata is flexible

    Don't let metadata perfection block design. Start with empty tags/pages and populate iteratively as you design.

    Document as you go

    Take screenshots during design iteration. It's easier to write narrative around existing screenshots than to retroactively document.

    One source of truth

    Keep versions.json and posts.json as the single metadata source. Don't duplicate in index.html or elsewhere.

    Meaningful tags

    Use consistent tag names. "boundary-upload" not "boundary", "map-styling" not "styling". This makes filtering and searching effective.

    Descriptive narrative

    Design history isn't a screenshot gallery. Explain: Why did we explore this? What did we learn? What changed?

    Getting started

    1. Open the home page: Prototype versions overview
    2. Click "Filter by feature" to explore existing versions by tag
    3. Click "View design history" to see documented releases and research
    4. When ready to create something new:
      • Run: @copilot #create-prototype-version
      • Or: @copilot #design-history-entry

    Questions? Refer to the skill documentation in .github/skills/ or ask Copilot.
