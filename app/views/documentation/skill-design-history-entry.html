Skill 2: Create a design history entry

Scaffolds folder structure, post template, and metadata for documenting design changes, releases, or research findings.

← Back to skills menu

Invoke: @copilot #design-history-entry

What it does

Scaffolds folder structure, post template, and metadata for documenting design changes, releases, or research findings.

Use when

  • Release is ready to document (what changed, why, screenshots)
  • Research findings need recording (what users struggled with, solutions tested)
  • Design iteration reaches a milestone worth explaining

Three ways to create a design history post

Option A: Version has no card yet

  • Run the skill — it creates everything including a card template
  • Copy the card template to index.html

Option B: Version card exists, create post manually

  • The version was created with #create-prototype-version, which added a card
  • Create the post manually (don't run the skill, see Alternative path below)
  • Update the existing card's design history link

Option C: Version card exists, automate post + screenshots (recommended)

  • Run the skill to generate post folder, screenshots, and posts.json entry automatically
  • Ignore the card template the skill generates
  • Update the existing card's design history link (just change date and designHistoryUrl in versions.json)
Alternative path: Create manually (no skill needed) — Option B only

If you prefer not to run the skill and the version card already exists:

  1. Create the folder: /app/views/design-history/3-9-0-0/
  2. Create index.html: Copy structure from an existing post (e.g., /app/views/design-history/3-7-0-2/index.html)
  3. Update versions.json: Add "designHistoryUrl": "/design-history/3-9-0-0/"
  4. Update index.html card: Change the link to point to your new design history post
  5. Update posts.json: Manually add an entry with version, date, url, title, type, tags, summary
  6. Add images: Place screenshots in /app/views/design-history/3-9-0-0/images/
  7. Write content: Fill in your post template with narrative and screenshots

This is slower than running the skill (no automation for screenshots or metadata), but completely avoids generating extra card templates.

When to use: You prefer manual control or don't want Playwright screenshot automation.

Workflow: from research to published post

Step 1: Prepare content (you do this)

Before running the skill, gather:

  • Screenshots/images (PNG format, max 2MB each, descriptive alt text)
  • Design narrative (what changed and why, 100-500 words)
  • Version identifier (e.g., 3.9.0.0 or draw-boundary-research)
  • Type: release / research
  • Date (e.g., "22 January 2026")
  • Feature tags (e.g., boundary-upload, map-styling)
Step 2: Run skill (Copilot does this)

Run the skill and provide:

  • Version identifier
  • Type (release or research)
  • Date
  • Title/heading
  • Summary (one-liner)
  • Feature tags

Copilot creates:

  • Folder: /app/views/design-history/3-9-0-0/
  • Post template: index.html with structure ready for content
  • Entry in: app/views/design-history/posts.json
  • Breadcrumb navigation set up
  • Also generates: HTML card template (use it only if you don't already have a card on index.html)

If a card already exists: Just ignore the generated card template and proceed to Step 3. You'll update the existing card's link later.

Step 3: Write content (you do this)

Edit the post template with your design narrative:

  1. Add introductory paragraph (context and goals)
  2. Add section for each key change/finding
  3. Add screenshots with descriptive captions
  4. Use heading hierarchy (h2 for major sections, h3 for subsections)
  5. Keep alt text meaningful: "Screenshot of new boundary drawing menu showing options for freehand vs polygon"

Structure: narrative + images, not a list. Tell the story of the design.

Step 3b: Auto-generate screenshots (optional)

Instead of manually taking screenshots, you can automate them:

Prerequisites:

  • Prototype server running locally (npm run dev)
  • Version's pages defined in versions.json

Run the helper script:

node scripts/screenshot-version-X-X-X.js --version X.X.X

Example:

node scripts/screenshot-version-3-6-1.js --version 3.6.1

What it does:

  • Takes full-page screenshots of all pages in your version
  • Saves them sequentially (01-page-name.png, 02-page-name.png, etc.)
  • Generates HTML snippet ready to paste into your post
  • Saves snippet to screenshot-snippet.html for easy copying

Then: Copy the generated HTML snippet and paste into your post template, edit alt text as needed.

⚠️ Important for deployment: The screenshot automation requires Playwright, which has peer dependency conflicts with the current @arcgis/core version. The .npmrc file includes legacy-peer-deps=true to handle this. If you ever run npm install without this flag, ensure you also run it with --legacy-peer-deps and commit the updated package-lock.json. Otherwise, Heroku deployments will fail with "npm lockfile is not in sync" errors.

Step 4: Publish (when ready)

Once content is complete:

  1. Verify all images are added and alt text is descriptive
  2. Check breadcrumb navigation (should link: Home → Design history → This post)
  3. Test links to prototype versions
  4. Commit to git

Post is now live at /design-history/3-9-0-0/ and linked from version card.

Linking to the version card:

  • No card exists yet: Copy the card template Copilot generated and paste it into index.html
  • Card already exists: Update it in index.html — change the date field and add design history link. You can also update versions.json with "designHistoryUrl": "/design-history/3-9-0-0/" and the card will update automatically.

⚠️ Avoid duplicate cards: Always search index.html for your version number before adding a new card. If it exists, update it instead.

Ready to document a design iteration? Run @copilot #design-history-entry in chat and provide the information from Step 1 above.
